# Family Decision Engine (FDE)

전세 만기라는 고정된 시점을 향해, 현재 자산·소득·대출·시장·근무지·육아를 동시에 넣어
**매수 / 전세 유지 / 다른 전세 / 반전세·월세 / 청약 대기** 중 무엇을 할지 계산하는 엔진.

집값을 맞히는 시스템이 아닙니다. 반대로, **집값을 예측하지 않고도 결론을 낼 수 있게**
만든 시스템입니다.

```
의존성:  Python 3.11+ 와 PyYAML.  그게 전부입니다.
         numpy/pandas/scipy 없음. Postgres 없음. 웹서버 없음.
```

## 0. 코드를 돌리기 전에 (30분, 코드 0줄)

이 저장소에서 **기대손실이 가장 큰 항목들은 프로그램이 아니라 당신이 해결합니다.**
아래 넷을 먼저 하세요. 이것만으로 이 시스템 기대가치의 상당 부분이 확보됩니다.

1. **등기부등본 열람** — 선순위 근저당 확인. 인터넷등기소, 700원, 5분.
2. **전세보증금반환보증 가입 여부 확인** — 미가입이면 가입 가능한지부터.
3. **계약갱신요구권을 썼는지 확인** — 이 불리언 하나가 결론을 뒤집습니다.
4. **캘린더에 만기 6개월 전 / 2개월 전 등록** — 통지 창을 놓치면 선택지가 사라집니다.

```bash
python3 -m fde check      # 위 항목을 상태 파일 기준으로 점검해 줍니다
```

## 2. 이 엔진이 내는 답의 형태

**내지 않는 것** — 점수판:

```
① 전세 유지   72점
② 다른 전세   81점  ← BEST
③ 매수        68점
```

72와 81의 차이는 아무 의미가 없습니다. 가중치를 5%만 바꾸면 순위가 뒤집히는데,
그 가중치의 근거를 댈 방법이 없기 때문입니다. 그리고 소수점까지 나온 숫자는
그 자체로 설득력을 갖기 때문에, 추측을 확신으로 바꿔놓습니다.

**내는 것** — 원 단위 격차 + 그게 뒤집히는 조건:

```
>>> B. 전세이사(직주근접-A)
    2위 'A. 전세유지' 대비 2,376만원 유리합니다.
    [주의] 격차가 3% 미만입니다. 사실상 동률이고 가정을 조금만 바꿔도 뒤집힙니다.

이 결론이 뒤집히는 조건:
 !! 주택가격 상승률이 2.83% 이상이면      → 매수로 뒤집힘 (현재 2.00%)
 !! 투자 기대수익률이 6.54% 이상이면      → 월세로 뒤집힘 (현재 5.00%)
 !! 전세보증금 상승률이 7.52% 이상이면    → 매수로 뒤집힘 (현재 3.00%)

매수 임계가격:
 - 직주근접-A: 매매가가 7.25억 이하(시세의 74%)면 매수가 최선입니다.
```

마지막 줄이 이 시스템의 존재 이유입니다. 부동산에 들고 갈 수 있는 유일한 숫자입니다.

## 3. 설계 원칙

### 3.1 예측이 아니라 임계값

"전세가가 몇 % 오를까?"는 답할 수 없는 질문입니다. 답한 척하면 정밀도의 환상이 됩니다.
대신 **"몇 % 이상이면 결론이 뒤집히는가"**를 계산합니다. 이건 예측 없이 계산 가능하고,
반증 가능하고, 월 1회 5분이면 넘었는지 확인됩니다.

그래서 이 시스템에는 데일리 크롤러가 필요 없습니다.

### 3.2 3단 분리 — 점수화하지 않는 것들

| 단계 | 내용 | 방식 |
|---|---|---|
| 1 | DSR·자기자본·통근상한·유동성·부담률 | **통과/탈락**. 점수화 금지 |
| 2 | 화폐화 가능한 전부 | **원 단위** 종료시점 세후 순자산 |
| 3 | 학군·만족도 등 잔여 | 사용자가 답한 **지불의사(WTP)**만 |

가중치를 지어내지 않습니다. "통근 20분 단축에 월 25만원 낼 의향이 있나"는 답할 수 있고,
"육아 25% 주거비 25%"는 답할 수 없습니다.

### 3.3 동일소비 정규화

모든 옵션에 같은 소득과 같은 생활비를 주고, 주거 현금흐름만 다르게 한 뒤
종료 시점 순자산을 비교합니다. 이렇게 하면 자동으로 맞아떨어집니다:

- **원금 상환은 비용이 아니다** — 순자산으로 이전되므로. 섞으면 매수가 부당하게 불리해집니다.
- **보증금은 비용이 아니다** — 자산 이동이므로.
- **유동성 부족이 드러난다** — 현금이 마이너스면 페널티 차입이 실제 비용으로 잡힙니다.
- **종료시점은 세후다** — 양도세·중개보수를 뺀 순현금.

### 3.4 정책은 코드가 아니라 데이터

LTV/DSR/취득세/특례대출은 수시로 바뀝니다. 코드에 하드코딩하면 6개월 뒤 조용히
틀린 답을 냅니다. 그래서 모든 정책값은 `config/policy/*.yaml` 에 `effective_from`,
`confidence`, `verified_on` 과 함께 둡니다.

**검증되지 않은 값이 결과에 실제로 영향을 준 경우에만** 리포트 최상단에 경고가 뜹니다.
이 프로젝트가 보는 최대 실패는 "틀린 답"이 아니라 **"확신에 찬 틀린 답"**입니다.

```bash
python3 -m fde policy-check    # 교체해야 할 항목 목록
```

### 3.5 상관 몬테카를로

금리 상승 + 자산가격 하락 + 소득 둔화는 따로 오지 않고 **같이** 옵니다.
독립 시나리오로 돌리면 진짜 위험한 꼬리를 못 봅니다.

목적함수는 기대값 최대화가 아니라 **하방 제약**입니다. 육아 가정에서 최적화 대상은
기대수익이 아니라 "아이 학기 중에 원치 않는 이사를 하게 될 확률"입니다.

### 3.6 재현성

모든 실행은 입력·정책·출력·git commit 을 `runs/<시각>_<해시>/` 에 봉인합니다.
3개월 뒤 결론이 바뀌었을 때 **시장이 변한 것인지 코드를 고친 것인지** 구분할 수
없으면 시스템 전체의 신뢰가 무너집니다.

## 4. 초안 대비 달라진 점

이 엔진은 원래 설계 초안을 점검한 결과를 반영한 것입니다. 주요 변경:

| 초안 | 이 구현 |
|---|---|
| 보증금 = 무위험 자산 | **`DepositRisk`** — 전세가율·선순위채권·역전세갭·보증가입으로 지연·손실 모델링 |
| 갱신요구권 없음 | **`renewal_right_used`** 1급 필드. 증액 상한이 '전세 유지' 비용을 결정 |
| 72점 vs 81점 | 원 단위 순자산 + 하드게이트 + WTP |
| 매수 비용에 원금 포함 | 이자/원금/보증금/일시상환 4분리 |
| 종료 청산가치 세전 | 양도세(1세대1주택 비과세, 장특공제)·중개보수 차감 |
| 전세/월세 이산 3옵션 | `deposit_ratio` 연속 변수 (반전세 포함) |
| 청약 없음 | 무주택 유지의 옵션가치를 5번째 선택지로 |
| 신생아 특례 없음 | 자격 게이트 + 금리 반영 (서울시 지원금보다 훨씬 큰 변수) |
| 독립 시나리오 5개 | 상관 몬테카를로 + 보증금 지연/손실 시나리오 추가 |
| 자체 DSR 계산 | **은행 사전조회값 우선**. 자체 추정은 경고와 함께만 |
| 육아비 상수 | 계단 곡선 (초등 입학에서 급증) |
| 점수 변화 알림 | 히스테리시스 + 행동가능성 게이트 |
| 검증 계층 없음 | 110개 테스트 + 백테스트 + 실행 스냅샷 |

## 5. 명령어

| 명령 | 설명 |
|---|---|
| `fde check` | 상태 검증 + 보증금 리스크. **가장 먼저** |
| `fde tradeoffs` | 부부 합의용 지불의사 질문지 |
| `fde policy-check` | 교체해야 할 정책 수치 목록 |
| `fde calendar` | 만기 역산 체크리스트 (하드 데드라인 표시) |
| `fde budget` | 목표 생활비 + 육아비 계단 곡선 |
| `fde buckets` | 현금 5버킷 + 글라이드패스 + 무엇을 팔지 |
| `fde decide` | 전체 리포트 (`--save` 로 스냅샷) |
| `fde sensitivity` | 결론이 뒤집히는 임계값 + 매수 임계가격 |
| `fde risk` | 상관 몬테카를로 하방 리스크 |
| `fde triggers` | 트리거 평가 (노이즈 억제) |
| `fde collect` | 시장 데이터 수집 (**월 1회면 충분**) |
| `fde backtest` | 시점을 옮겨가며 결론 안정성 측정 |

## 6. 데이터 수집에 대해

```bash
export ECOS_API_KEY=...      # 한국은행 ECOS (금리)
export DATA_GO_KR_KEY=...    # 공공데이터포털 (국토부 실거래가)
python3 -m fde collect
```

키가 없으면 **조용히 건너뛰고** 나머지 기능은 그대로 동작합니다.

- **수집함**: 실거래가(매매/전세/월세), 기준금리·대출금리·수신금리
- **수집 안 함**: 포털 호가 크롤링. 약관 위반이고, 호가는 실거래가 아니라 노이즈입니다.
- **수동 입력**: 입주물량. 공식 API가 없습니다. `data/supply.csv` 에 출처 주석과 함께.

실거래가는 정제 없이 쓰면 **최근 1개월 시세가 항상 왜곡됩니다.** 파이프라인이
신고지연 구간 제외 → 취소·직거래 제외 → 면적 한정 → MAD 이상치 제거 →
최소 표본 검사를 거칩니다.

**빈도**: 일 단위 수집은 가치가 거의 없습니다. 만기 전에는 행동 공간이 거의 닫혀
있어 매일 수집해도 바뀌는 결정이 없습니다. 월 1회로 충분하고, 그러면
크롤러 유지보수 부담이 사라집니다.

## 7. 이 시스템이 하지 못하는 것

정직하게:

- **집값을 예측하지 못합니다.** 하려고도 하지 않습니다.
- **당신의 정책값이 틀리면 답도 틀립니다.** 그래서 경고를 그렇게 크게 냅니다.
- **은행 대출한도를 대신하지 못합니다.** 사전조회 결과를 넣어야 정확합니다.
- **격차가 작으면 답이 없습니다.** 3% 미만 격차는 "어느 쪽이든 큰 차이 없다"가
  정직한 해석이고, 그때는 통근·육아·안정성 같은 비화폐 요인으로 결정하세요.
- **부부 합의를 대신하지 못합니다.** 질문지를 줄 뿐입니다. 그게 실제 병목입니다.

가장 중요한 한계: **이 결정은 2년에 한 번 일어납니다.** 시스템의 가치는 매일
돌리는 데 있지 않고, 만기 역산 캘린더 · 보증금 안전장치 · 임계값 세 가지에
있습니다. 나머지는 그 셋을 반복 가능하고 검증 가능하게 만드는 장치입니다.
